# Android: библиотеки, дизайн и проверка

- По решению пользователя в спорных случаях выбирать поддерживаемые готовые
  библиотеки и стандартные компоненты. Сначала проверять возможности Material 3,
  Compose Foundation, Media3 и профильных библиотек, затем писать собственный код.
- Не создавать собственный движок графиков, календаря, плеера, жестов или галереи,
  если существующая библиотека покрывает нужный сценарий. Собственный код отвечает
  за данные приложения, бизнес-логику, оформление и интеграцию компонентов.
- Проверять совместимость и лицензию зависимости; фиксировать версию. Сохранять
  функции веб-версии при замене компонента, включая редкие виды диаграмм.
- Все компоненты должны следовать общей теме: типографика, оси, цвета, отступы,
  состояния загрузки/ошибки/пустых данных. Наличие библиотеки не заменяет дизайн.
- Принимать UI после просмотра реальных открытых экранов, прокрутки и действий
  в обеих темах; тестировать телефон, планшет и увеличенный шрифт.
- Работать в `main`. Незавершённые версии не публиковать даже как prerelease.
  Рабочие APK и снимки оставлять локально для проверки.
- Устойчивая очередь записей — Room, фоновая работа и её повтор — WorkManager.
  Не дублировать их JSON-очередями в настройках или собственным циклом backoff.
- Перед переходом экрана подтверждать локальную транзакцию, не ожидание HTTP.
  Проверять правку и отмену при задержанном ответе сервера; не выполнять I/O в UI-потоке.
- Черновики не читать из SQLite внутри Composable и не записывать синхронно при
  каждом символе. Использовать Room/Flow, асинхронную загрузку и flush при уходе в фон.
- Операции разных экранов, чат и каталог имеют отдельные состояния. Отменять
  запросы при выходе; старое завершение не должно менять состояние нового сеанса.
- Постоянный офлайн-статус не показывать перекрывающим экран Snackbar.
  Большие списки строить на Lazy-компонентах со стабильными ключами.
