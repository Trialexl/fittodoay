# Локальная отзывчивость и готовые компоненты — 0.4.4-dev

Работа в `main`. Backend и его контракт не меняются. Релиз не публикуется.

## Найденные причины задержек

Завершение отдыха ожидало POST/PATCH и GET плана, прежде чем закрыть экран.
Общий `busy` блокировал навигацию и тренировочные кнопки. Запись очереди,
кеша и состояния таймера выполнялась синхронно в потоке интерфейса.
Появление индикатора и сообщений меняло высоту всей страницы. Музыкальный
каталог в настройках целиком размещался в обычной Column.

## Используемые решения

| Было | Теперь |
|---|---|
| JSON-очередь и планы в SharedPreferences | Room 2.7.1, транзакции, схема и Flow; однократный перенос существующих данных |
| Сохранение интерфейса после ответа сети | Локальная транзакция, обновление интерфейса и отдельная отправка |
| Повторная отправка через полную загрузку экрана | WorkManager 2.10.1 с ограничением по сети и backoff; короткий foreground drain той же очереди |
| Блокирующий HTTP execute при отмене экрана | Асинхронный OkHttp Call с отменой coroutine/socket |
| Запись таймера и разбор плана в UI-потоке | Dispatchers.IO/Default; AlarmManager остаётся источником системного сигнала |
| Ручные рамки числового поля и кнопки Surface | Material 3 TextFieldDefaults.DecorationBox и OutlinedIconButton; Foundation ввод |
| Старый дублирующий NumberControl | Удалён; один компонент числового ввода |
| Полный музыкальный каталог в Column | Foundation LazyColumn в ограниченной по высоте панели |
| Мгновенная смена экранов и сворачивание | Compose AnimatedContent/AnimatedVisibility, штатные анимации прогресса и цвета |
| Сообщение, сдвигающее страницу | Material 3 SnackbarHost; фиксированное место тонкого индикатора |

Room обеспечивает хранение и транзакции, WorkManager — устойчивую фоновую работу,
Compose/Material — отображение и анимации. Код приложения сопоставляет поля API,
сохраняет последнее намерение пользователя и разрешает ID подхода после
неопределённого результата POST. Это предметная логика существующего API.

Подход, правка, отмена и вес сначала сохраняются локально. Поздний ответ не
удаляет новую редакцию очереди. Отмена во время POST оставляет операцию DELETE,
поэтому завершившийся запрос не возвращает отменённый подход в чеклист.
Старый GET не заменяет более свежую локальную версию. Перед серверным анализом
тренировки ожидается отправка результатов, чтобы ассистент получил актуальные данные.
При переходе от отдыха к сохранённому результату один подход больше не считается
одновременно записанным и ожидающим: день и упражнение не сворачиваются раньше времени.
Профильный UI-тест проверяет, что после первого из двух подходов день остаётся открытым.

## Проверки и ограничения

- JVM debug/release: по 60/60, без ошибок и пропусков.
- Lint debug/release: 0 ошибок, 31 предупреждение; frontend lint без замечаний.
- Room и задержанный HTTPS: 6/6; тренировочные сценарии: 4/4.
- Живой API синтетического аккаунта: 5/5; увеличенный шрифт: 3/3,
  включая плейлист с клавиатурой, видео после фона и офлайн-вес.

Новый профиль использует локальный HTTPS-сервер и синтетическую сессию. Ответ
сервера удерживается после записи, пока в настоящем UI выполняется правка или
отмена. Эти тесты не пишут тренировочные данные на production-сервер.
В профильном прогоне возврат в чеклист занял 289–388 мс; проверка
StrictMode не обнаружила обращений к хранилищу в UI-потоке тренировочных действий.
Проверены поздний ответ, отсутствие дубля, отмена без восстановления записи,
перенос старой очереди в Room и изоляция аккаунтов.

Функциональные тесты используют штатный MotionDurationScale=0: непрерывно
анимированный циферблат не является критерием Espresso idle. Анимация
сворачивания отдельно проверяется с включённой анимацией по промежуточной высоте
реальной карточки в конце прогона; последующие touch-события не смешиваются с остановленными часами. Визуальная матрица работает с обычным масштабом анимаций.

FrameMetrics на программном GPU эмулятора не подтверждают частоту кадров
физического телефона. Обещания 60 fps нет. Полная сверка приложения с вебом и
проверка физического устройства остаются отдельными незавершёнными проверками.
Постоянная ошибка валидации API сохраняет данные в очереди и показывает причину;
автоматическое разрешение конфликта с удалённым на сервере упражнением не добавлено.
Очередь результатов переведена на WorkManager. Старое полное зеркалирование
архива и хранение черновиков чата пока сохраняют прежнюю реализацию; их
переработка не входит в эту итерацию и не считается завершённой.

Основа подхода: [offline-first Android](https://developer.android.com/topic/architecture/data-layer/offline-first),
[Room](https://developer.android.com/training/data-storage/room),
[WorkManager](https://developer.android.com/topic/libraries/architecture/workmanager).

Заключительная визуальная матрица: 4/4 — 393/360 dp, планшет 1067 dp,
шрифт 130%, обе темы, семь диаграмм и промежуточное состояние раскрытия.
Аудио: 2/2 прогона, три сценария (передний план, фон, запрет уведомлений).
Проверены реальный audio focus Android, приглушение и восстановление музыки.
Точный подписанный APK установлен на отдельный AVD; hash совпал, экран входа
нативный, debug и WebView отсутствуют. Серверные сценарии release этим тестом
не проверяются. Локальная галерея: `artifacts/fluid-review/index.html`,
97 снимков. Публикации нет.
