# AI Agents in fitTODOay

## 1. Scope and Responsibilities

- **LLM Workout Assistant** – единственный агент в проекте. Его задача: на основании краткой анкеты пользователя (пол, возраст, цель, количество тренировок и т.д.) предложить персонализированные программы и дни тренировок, используя только упражнения из нашего каталога.
- Агент запускается в разделе «Создать с помощником» на фронтенде и общается с бэкендом через `POST /api/llm-agent/programs/`.
- Все вычисления (запросы к OpenRouter, валидация, создание ProgramFolder/DayTemplate/TemplateExercise) происходят на стороне backend, чтобы API-ключ и логика оставались защищёнными.

## 2. Архитектура и Поток данных

```
Frontend wizard → POST /api/llm-agent/programs/ → Backend LLM service
  → OpenRouter (LLM) → Backend пост-обработка
  → создание ProgramFolder / DayTemplate / TemplateExercise
  → ответ фронту (JSON + резюме программ)
```

### Backend → LLM
- Используется OpenRouter (`OPENROUTER_API_KEY`, `OPENROUTER_MODEL` из `.env`).
- В payload отправляются: профиль пользователя (без персональных данных – ID, e-mail и т.п. не передаём), список доступных упражнений (ID, название, мышцы, параметры `has_weight`/`has_time`) и ограничения по количеству программ/дней.
- Ответ ЛЛМ должен соответствовать JSON-схеме (программы → дни → упражнения). При несоответствии или тайм-ауте возвращаем `503` и сообщение «создание через помощника недоступно…».

## 3. Требования к UX и сохранению данных

- Визард многократный: любые поля можно редактировать, ответы сохраняются в профиле (`llm_preferences`) и подтягиваются при повторном запуске.
- После генерации пользователь видит список программ: одна активная, остальные выключены. Можно пересоздать, вручную поправить через ProgramBoard или вернуться к обычному режиму.
- Ошибки агента (LLM недоступен, неверный JSON) логируются на backend, но пользователю возвращаем дружественный fallback.

## 4. Контроль качества и логирование

- Backend логирует каждое обращение к LLM (ID пользователя, время, payload/ответ без PII, статус). Это нужно для отладки и соблюдения требований безопасности.
- Тестовые сценарии описаны в `docs/test-plan.md` (раздел LLM) – проверяем успешное создание, обработку ошибок, повторный запуск с сохранёнными данными.
- UX детали и копирайт – `docs/prd-llm-agent.md` и `docs/prd-frontend.md`.

## 5. Работа над агентом

- Все задачи по ассистенту фиксированы в `docs/task.md` (раздел «Подготовка LLM-агента»). Перед изменениями проверяйте связанные документы (PRD, тест-план).
- Фронтенд реализация находится в `frontend/src/app/assistant/page.tsx` и использует Wizard на хуках + `apiFetch`.
- Backend логика – `backend/workouts/services.py` (обработчик LLM-потока) и API `/api/llm-agent/programs/`.
- Любые изменения в `frontend` (включая правки UI, хуков, стилей или конфигов) не принимаются без линта: из каталога `frontend` запускайте `npm run lint` после каждого блока правок и перед любым PR/коммитом, добиваясь чистого вывода.
- При необходимости документации или информации о зависимостях обязательно используем Context7 (MCP) и сверяемся с доступными библиотеками через `resolve-library-id`/`get-library-docs`.
- Правило завершённости: не оставляй задачи наполовину. Если цель поставлена, доводи до полного соответствия требованиям. Перед паузой или остановкой самопроверь, закрыта ли задача целиком; если нет — продолжай, пока не будет готово.

## 6. MCP / Context7

- Для доступа к внешней документации (Context7) используем MCP клиент Codex. Конфигурация в `~/.codex/config.toml` должна содержать секцию:
  ```toml
  [mcp_servers.context7]
  command = "npx"
  args = ["-y", "@upstash/context7-mcp"]
  ```
- Перед использованием убедитесь, что сервер доступен и отвечает на запросы `list_mcp_resources`/`get-library-docs`. При ошибках (например, `Method not found`) сверяйтесь с документацией Context7 и обновляйте конфиг/эндпоинты.

Этого документа должно хватить, чтобы быстро понять роль и требования к LLM-агенту в fitTODOay.
