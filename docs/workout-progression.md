# Рекомендации после тренировки: progression-v1

## Контракт и границы

Данные `WorkoutDay.plan_snapshot` и `WorkoutSetLog` → `WorkoutAnalysisSnapshot` →
решения policy → строгая проверка → объяснение LLM → существующие карточки чата →
повторная проверка → применение пользователем.

Снимок строится отдельно для каждого TemplateExercise, принадлежность проверяется по
пользователю, программе и DayTemplate. План берётся из исторического снимка дня, фактические
повторы/веса — из подходов именно этого дня. До трёх предыдущих сессий упражнения передаются
отдельно. Историческое среднее `exercise_trend` служит только контекстом и не является текущим
рабочим весом. Сессии после выбранной даты исключены. Планы без логов не входят в тренды и
не прерывают поиск предыдущей фактической аналогичной тренировки.

`previous_similar_workout_date`, `days_since_similar_workout`, `return_after_break`
рассчитывает backend. Аналогичность определяется устойчивым ID DayTemplate, а история
упражнения дополнительно разделена по ID/типу источника. Незавершённое упражнение остаётся
в снимке, но получает `hold / INCOMPLETE_SESSION / missing_sets_not_assessed`. Это не отказ.
Пропуск одного упражнения не блокирует остальные. Для полноты нужны именно ожидаемые индексы
подходов, а не просто совпадение количества строк.

При повторной загрузке прошедшего дня с логами его план больше не перестраивается
из текущей программы. В текущем дне сохраняются исходные карточки упражнений,
в которых уже есть подходы; ещё не начатые и новые упражнения продолжают обновляться.
Поэтому подтверждённое повышение веса/повторов относится к следующим тренировкам и
не переписывает цели уже выполненного упражнения. Статус дня проверяется по всем
ожидаемым парам (упражнение, индекс подхода); лишняя запись не заменяет пропущенный
подход. При обновлении состава плана статус пересчитывается.

RIR/RPE/pain остаются `null`: полей пользовательского ввода в модели сейчас нет.
Искусственный `average_reps - 8` удалён и из старого алгоритма. Новых полей усилия/боли
и соответствующих UI-кнопок эта версия не добавляет. Ветка PAIN_LIMITED предусмотрена
для будущих явных измерений, но текущий адаптер не создаёт такие данные.

## Политика

- FIRST_SESSION: нет завершённой истории этого упражнения → база, без изменения плана.
- RETURN_AFTER_BREAK: предыдущий фактический день того же типа был ≥14 дней назад.
  Сохраняем нагрузку. Единственное изменение: одинаковый более высокий вес во всех
  подходах с выполнением текущей цели позволяет точно синхронизировать вес плана.
  Повторы при синхронизации сохраняются, вес не округляется вверх.
- NORMAL_PROGRESSION: все подходы завершены и достигли цели при плановом весе → +1 повтор
  до 12. Все подходы достигли 12 в двух последовательных сопоставимых сессиях → +2 кг,
  новый цикл с 8. Среднего результата недостаточно для подтверждения верхней границы.
- REGRESSION для упражнений с весом: все подходы ниже 8 на двух последовательных завершённых сопоставимых
  сессиях → −2 кг, минимум 0. Возвратная тренировка не засчитывается в подтверждение.
- Неполные данные, разные рабочие веса или переменный план подходов ограничивают анализ;
  отсутствие изменения — полноценное решение hold с reason_code и фактическими evidence.

Диапазон 8–12 и шаг 2 кг — константы первой версии. Планы с целью вне 8–12
сохраняются без автоматического изменения (unsupported_rep_range). Timed/static упражнения сохраняются
без изменения. Уменьшение объёма, отдых, учёт порядка, веса тела, e1RM/EWMA, техника,
необычный отдых и персональные шаги веса пока не автоматизированы: соответствующих
надёжных наблюдений/контракта в этом движке нет. Тоннаж не определяет решения упражнения.

## Actions, объяснения и применение

Backend создаёт canonical action с `type=update_exercise`, `template_exercise_id`,
`day_id`, `program_id`, `workout_day_id`, `policy_version`, `changes.from/to`,
`reason_code`, `evidence`. Валидатор пересчитывает предложение из БД и сравнивает его
целиком, проверяет владение, точное название, существование изменения и актуальность
плана/логов. Более поздняя фактическая тренировка делает старое предложение неактуальным.

Первичный запрос `post_workout_review` передаёт LLM policy_decisions и только проверенные actions.
Все actions из её ответа отбрасываются. Она формулирует только `assistant_reply`.
Для существующего UI backend переводит действие в привычные flat-поля `update_weight`,
сохраняя canonical proof в `policy_action`; применение использует только этот proof,
повторно проверенный по БД. Передача flat-поля LLM не может изменить числовое решение.
Подтверждение сериализовано транзакцией; повторное применение закрытого предложения отклоняется.

Продолжение диалога использует `post_workout_chat`: сохраняет статистику выбранной
программы, историю и `proposal_state` (pending и последнее применённое/отменённое
предложение). Отвечает на текущий вопрос; явная ручная правка пользователя создаёт
обычное pending-действие с точным ID и снимком программы. Shadow не запрещает такие
ручные правки. Текст предложения строится сервером из проверенных действий и текущего
плана: он не может выдавать подготовку предложения за сохранение. Вопросы без новых
действий сохраняют прежний pending и кнопку применения. Новое предложение заменяет старое.
Старые клиенты, отправляющие каждый вопрос как post_workout_review, автоматически
переходят в диалог после первого ответа в чате. Начальный автоматический разбор
по-прежнему не принимает действий LLM. Успешные логи содержат requested_mode/effective_mode.

В аналитике и тренировке первый запрос — review, последующие — chat. Аналитика получает
данные программы с backend, а не передаёт в prompt общую статистику всех программ.
Результат применения и статус предложения видны в чате; повторное применение и
устаревший снимок проверяются прежним механизмом.
`hold` без `changes` сохраняет текущие параметры плана: при плане 140 кг и факте
120 кг это не означает перенос фактических 120 кг в план. Это различие явно задано
в prompt обоих режимов и проверено на локальном QA-примере с реальной моделью.
Короткие вопросы о подтверждении («А как зафиксировать?», «Сделаешь?», «Сломался?»,
«Теперь в плане 120?») обрабатываются сервером без вызова LLM. Ответ использует
реальный pending/applied/cancelled и текущие значения БД, а не старый текст предложения.
Остальные вопросы и ручные правки остаются диалогом с моделью; `reply_source` в логе
различает серверный статус и ответ LLM.

Для ручного чата редактирования программы сохраняются существующие действия добавления,
замены и удаления. Для любого update обязателен точный `template_exercise_id`; каталоговый
`exercise_id` запрещён. Несовпадающее название/день/программа отклоняются до локализации
карточки. Ошибки нормализации сохраняются в `LLMRequestLog.response.action_validation_errors`.

## Предложения с подтверждением и режим сравнения

С 07.11.2026 по умолчанию `WORKOUT_PROGRESSION_MODE=active`: проверенные решения
движка показываются карточками. Программа меняется только после нажатия
«Применить изменения», а не после разбора или сообщения в чате. Завершение всего дня
не требуется: при 3/21 подходах завершённое упражнение может получить предложение,
а остальные упражнения сохраняют план и не считаются неудачными.

Для аудита можно явно установить `WORKOUT_PROGRESSION_MODE=shadow`. Движок сохраняет
`WorkoutAnalysisRun`: снимок, решения, canonical actions и результат старого детерминированного
алгоритма. При первичном автоматическом разборе новые policy-действия не становятся pending,
LLM-действия также не становятся pending. Последующий явный ручной запрос пользователя
может создать отдельное обычное pending-предложение. Пользователь получает понятное
объяснение доступности предложений, без названий режимов и кодов действий.
Ручное редактирование и подтверждение явных пользовательских правок доступны в обоих режимах.
Старый `/api/workouts/recommendations/` остаётся legacy-контрактом для сравнения и прежнего
ручного интерфейса; новый механизм подтверждения используется в post-workout чате.
Старый алгоритм исправлен по полноте отдельных упражнений и искусственному RIR, но его
исторические правила не являются новой политикой. Не использовать legacy endpoint как
источник новых policy-actions.

Добавлена миграция `0022_workoutanalysisrun`. Журнал доступен в Django admin только для чтения.
Повторный анализ обновляет отчёт этого дня/программы/версии, без повторного подсчёта как
отдельной тренировочной сессии. Журнал не является неизменяемым архивом версий логов.

Ретроспектива без изменения программы (по умолчанию не пишет даже отчёты):

```sh
docker compose run --rm backend python manage.py replay_workout_policy --program-id <ID> --limit 20
```

Добавьте `--save`, чтобы сохранить сравнения в журнале. В отчёте каждой сессии есть legacy,
новые решения, действия и финальный счётчик `programs_changed: 0`. Сравните минимум 10–20
реальных тренировок, отдельно проверив возвраты, неполные дни и смены веса/упражнений.
Синтетический прогон 20 сессий покрыт тестом; он не заменяет ретроспективу реальных данных.

Явное значение в backend environment имеет приоритет над новым значением по умолчанию.
Если ранее в `backend/.env` был указан `shadow`, для карточек требуется заменить его на
`active`. Это включает карточки, но не автоматическое изменение программы.
После изменения кода без bind mount обязательны:

```sh
make build-backend
docker compose up -d --no-deps backend
```

Проверки реализации:

```sh
docker compose run --rm backend pytest workouts/test_progression.py workouts/tests.py agents/tests.py -q
```

оценки «Супермена», название тяги и отсутствие карточек применения в shadow. В тестовом
active-окружении проверить ровно 34→36 кг при неизменных 8 повторах; изменить план до
подтверждения и убедиться, что устаревшее предложение пропускается с понятной причиной.
