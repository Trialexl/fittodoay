# PRD — LLM Workout Program Agent

## 1. Цель и контекст
- Сократить время настройки тренировочных программ: пользователь отвечает на несколько вопросов, и ассистент генерирует подходящую структуру программ/дней/упражнений на базе нашего каталога.
- Решение должно быть расширяемым: сначала документируем и проектируем, затем добавляем API и фронт.
- Генерация происходит на стороне backend через OpenRouter (LLM). Ключ хранится в `.env` (`OPENROUTER_API_KEY`) и не попадает на фронт. Дополнительно задаём `OPENROUTER_MODEL` для выборной модели.

## 2. Пользовательский сценарий (Wizard)
1. Пользователь открывает раздел «Создать с помощником».
2. Ассистент уточняет:
   - Пол
   - Возраст
   - Вес
   - Цель (например, похудение/набор/сила/поддержание и т. д.)
   - Сколько тренировок в неделю
   - Средняя продолжительность одной тренировки
3. После заполнения ассистент формирует предложения программ. Можно предложить несколько вариантов; один автоматически делается активным, остальные — деактивированы.
4. Пользователь просматривает результат, при необходимости вручную корректирует.

### Требования к визарду
- Ненавязчивый: по шагам, без блокирующих модалок; в любой момент можно вернуться к ручному созданию.
- Сохранение ответов в профиле пользователя (например, `user.profile.llm_preferences`). При повторном запуске визард предзаполняется, но пользователь может редактировать каждое поле.
- Возможность повторного запроса: пересоздавать программы с обновлёнными параметрами.

## 3. Общая архитектура
```
Frontend Wizard → Backend endpoint `/api/llm-agent/programs/`
  → OpenRouter (LLM) → Backend пост-обработка
  → Создание ProgramFolder/DayTemplate/TemplateExercise
  → Ответ фронту (JSON + краткое описание)
```

### Интеграция с OpenRouter
- Backend использует `OPENROUTER_API_KEY` и `OPENROUTER_MODEL`.
- Все запросы идут только с сервера; логируем payload (без персональных данных) и ответ LLM.
- Формат запроса: система/инструкции + данные пользователя + список доступных упражнений (см. ниже).

## 4. Формат данных

### Вход (frontend → backend)
```json
{
  "gender": "male|female|other",
  "age": 32,
  "weight": 82,
  "goal": "fat_loss",
  "sessions_per_week": 4,
  "session_duration": 60
}
```

### Backend → LLM (основа)
```json
{
  "user_profile": { ... как выше ... },
  "available_exercises": [
    { "id": 101, "name": "Жим лёжа", "target_muscles": "грудь/трицепс", "has_weight": true, ... }
  ],
  "constraints": {
    "max_programs": 3,
    "min_days_per_program": 1,
    "max_days_per_program": 7
  },
  "output_schema": {
    "programs": [
      {
        "name": "string",
        "is_active": true,
        "days": [
          {
            "name": "string",
            "comment": "optional",
            "exercises": [
              {
                "exercise_id": "number (из нашей базы)",
                "sets": 4,
                "reps": 12,
                "weight": 30,
                "time": null,
                "rest": 60,
                "note": "optional"
              }
            ]
          }
        ]
      }
    ]
  }
}
```
> **Важно:** LLM возвращает только ID упражнений из нашего каталога; никакие новые упражнения не создаются.

### Ответ LLM → backend
- JSON по описанной схеме.
- Backend валидирует: существуют ли упражнения, корректны ли числа, не превышены ограничения.
- При ошибке/несоответствии — логируем, пользователю показываем fallback.

## 5. Backend API
- `POST /api/llm-agent/programs/`
  - Тело: данные визарда.
  - Действия:
    1. Берём предпочтения пользователя (если есть) и мержим с входом.
    2. Собираем каталог упражнений (упрощённый список) и отправляем LLM.
    3. Получаем ответ, валидируем.
    4. Создаём ProgramFolder (если нужно) и DayTemplate + TemplateExercise. Основная программа активна, остальные — `is_active = False`.
    5. Возвращаем созданные сущности и резюме (пример: `{ "created_programs": [...], "active_program_id": 12 }`).
  - Логирование: сохраняем JSON запроса/ответа (без персональных данных: не логируем email, но можно логировать ID пользователя + hash).
  - Тайм‑аут/ошибка LLM: возвращаем 503 + сообщение "На данный момент создание через помощника недоступно. Можете попробовать позже или создать программу вручную."

## 6. Frontend UX (обзор)
- Раздел «Создать с помощником»:
  - шаг 1: ввод/подтверждение параметров (prefill с сервера).
  - шаг 2: обзор результата (карточки программ, дни, список мышц).
  - шаг 3: действия: активировать/пересоздать/перейти к редактированию вручную.
- Визард не блокирует основную навигацию. Можно отказаться в любой момент.

## 7. Сохранение и повторное использование данных
- Backend хранит предпочтения в профиле пользователя (например, поле `llm_preferences` в `UserProfile`).
- При следующем визарде API возвращает эти значения; фронт отображает их в inputs с возможностью изменения.
- Отдельный endpoint (например, `GET /api/llm-agent/preferences/`) может отдавать сохранённые данные.

## 8. Логирование и мониторинг
- Логируем:
  - ID пользователя
  - Время запроса
  - Payload (обезличенный)
  - Ответ LLM (обезличенный)
  - Ошибки (тайм‑аут, парсинг, валидация)
- Персональные данные (email, имя) не отправляем в LLM и не пишем в лог.
- Желательно добавить флаг `llm_agent_enabled` для отключения на уровне конфигурации.

## 9. Ошибки и fallback
- Если LLM недоступен/вернул ошибку/JSON невалиден:
  - Backend отдаёт `{ "detail": "assistant_unavailable" }` и сообщение: «На данный момент создание через помощника недоступно. Можете попробовать позже или создать программу вручную».
  - Фронт показывает баннер + ссылку на ручное создание.
- Если часть программ удалось создать, но часть нет — либо откатываем всё, либо создаём только валидные (решение в реализации, но лучше атомарно).

## 10. Риски и открытые вопросы
1. **Актуальность каталога** — нужно обеспечить, чтобы LLM всегда получал свежий список упражнений (ограничить до топ‑N?).
2. **Стоимость запросов** — зависит от модели OpenRouter; стоит добавить rate limiter.
3. **Время генерации** — предупреждать пользователя, если ожидание > 5 секунд (показать индикатор).
4. **Мульти-язычность** — LLM должен формировать названия/комментарии на русском (указать в system prompt).
5. **Валидация** — нужно строго проверять, что ID упражнений существуют, и числовые значения в допустимых диапазонах (например, `sets <= 10`).
6. **Хранение истории** — пока не требуем, но возможно понадобится вести журнал сгенерированных программ для аудита.
