# PRD — помощник тренировочных программ

Актуальный контракт: 05.11.2026. Этот документ описывает генерацию программ и чат
редактирования; рекомендации после тренировки остаются отдельным backend policy engine.

## Назначение

Помощник подбирает упражнения из действующего каталога с учётом цели, опыта,
оборудования, ограничений и пожеланий. API-ключ и исполнение инструментов находятся
на backend. Имя, e-mail и идентификатор аккаунта не отправляются модели. Свободный текст
пользователя и фитнес-профиль передаются как контекст; пользователь может сам включить
персональные сведения в свободный текст.

## Генерация с подтверждением

1. Визард загружает сохранённые предпочтения из `/api/profile/preferences/`.
2. `POST /api/llm-agent/programs/preview/` принимает поля анкеты и сохраняет предпочтения.
3. Backend передаёт профиль и ограничения модели. Модель получает каталог через инструменты.
4. Весь план проверяется до записи программ: ровно одна программа, 1–5 дней,
   1–8 упражнений в день, существующие и прочитанные через инструменты ID, числовые
   границы, тип нагрузки, расписание и распознанное оборудование профиля.
5. Создаётся `LLMProgramDraft`, а не `ProgramFolder`. Ответ: `draft_id`, `plan`
   с названиями упражнений, `expires_at`. Черновик действует 24 часа.
6. Пользователь просматривает дни, упражнения и параметры, нажимает «Сохранить программу».
7. `POST /api/llm-agent/programs/drafts/<uuid>/apply/` проверяет владельца, срок,
   актуальность профиля и план, атомарно сохраняет программу. Повтор возвращает тот же
   результат без дубликатов. Изменение профиля во время генерации также выявляется.

Прежний `POST /api/llm-agent/programs/` сохранён для совместимости: он сразу сохраняет
валидную программу. Визард использует только preview/apply. Генерация не создаёт
пользовательские упражнения. Неизвестный рабочий вес остаётся null.

## Чат программы

Контекст включает текущую программу, точные ID её дней и упражнений, расписание,
активность, фактические параметры с defaults, фитнес-профиль и последние 12 сообщений.
Текущее сообщение не дублируется. Фиксированной предварительной выборки каталога нет.

Доступные инструменты только читают данные:

| Инструмент | Назначение |
| --- | --- |
| `search_exercises` | Ключевые слова движения + отдельные фильтры мышц и оборудования, total/offset |
| `get_exercise` | Карточка, техника, основные/вспомогательные мышцы, оборудование |
| `get_profile` | Актуальный фитнес-профиль и пожелания |
| `get_program` | Только обсуждаемая программа текущего пользователя; в генерации отсутствует |
| `list_custom_exercises` | Только собственные упражнения пользователя |

Аргументы проверяются на backend; неизвестные поля/инструменты и превышения лимитов
возвращаются модели как ошибки. Цикл ограничен четырьмя обращениями к модели,
восемью вызовами инструментов и общим сроком 75 секунд. Финальный ответ формируется
отдельно по JSON Schema: Gemini 2.5 не принимает инструменты и response_format вместе.
Границы размеров плана/действий проверяет backend; вложенные maxItems не передаются
провайдеру из-за ограничения сложности схемы Gemini.

Модель предлагает `add_exercise`, `replace_exercise`, `remove_exercise`,
`update_weight`, `create_custom_exercise`; сами инструменты ничего не применяют.
Каталожное упражнение для добавления/замены должно быть прочитано через инструмент.
Если модель использует ID из истории без актуального чтения, backend возвращает ей
`exercise_not_read_by_tool` внутри того же ограниченного цикла и предлагает вызвать
`get_exercise`; без исправления действие не попадает в pending.
Изменение существующего упражнения требует однозначного ID записи программы.
Неизвестное или неоднозначное название не заменяется похожим. Создание своего
упражнения предлагается только после поиска и явного запроса пользователя.

Перед показом pending-предложения проверяются типы, числа, принадлежность программы,
дня/упражнения, источник и доступное распознанное оборудование. Предложение привязано
к снимку программы, переданному модели. «Применить изменения» повторно проверяет
актуальность и блокирует конкурирующее подтверждение; при изменении программы требуется
новое предложение. Старые pending-предложения отменяются при новом ответе.
Каждое действие имеет отдельный savepoint: неудачное действие полностью откатывается,
остальные могут примениться. UI оставляет чат открытым и показывает применённые и
пропущенные изменения с причинами.

## Поиск и качество каталога

Редактор, внутренние инструменты и внешний OAuth MCP используют общий поиск.
Явные условия соединяются через AND. По умолчанию поиск в редакторе, внутренних
инструментах и MCP учитывает основные и вспомогательные мышцы (`primary_only=false`).
`primary_only=true` используется только по явному запросу исключительно основных мышц.
Внутренний помощник ограничен серверной политикой: если в текущем запросе чата
(или пожеланиях генерации) нет явного требования «только основные мышцы», backend
выполняет поиск с primary_only=false даже при primary_only=true от модели.
Совпадение по основной мышце получает больший вес, точное название сохраняет приоритет.
В ответе помощник поясняет роль мышцы, не выдавая вспомогательную за основную. Поддерживаются ё/е, частые
русские/английские названия и формы слов, точное название имеет приоритет.
«Разведения» также находят боковые подъёмы (lateral raise); жимы и подъёмы перед собой
не приравниваются к этому движению. Направление и положение тела в запросе сохраняются.
В неоднозначном запросе помощник уточняет вариант, не предполагая просьбу добавить его. Нет случайной
алфавитной подстановки при нулевом результате. Модель должна уточнить запрос, а не
молча снимать ограничения; одна страница не означает конец каталога.

Это детерминированный поиск с явными синонимами, не полнотекстовая анатомическая
экспертная система. Качество зависит от исходных мышц и оборудования в каталоге.
`python manage.py audit_exercise_catalog` выводит проблемы метаданных и recall@5
контрольных запросов, не изменяя каталог. Начальный аудит: 874 упражнения, у 1 нет
основной мышцы, у 77 не заполнено оборудование, 27 предупреждений о возможном
конфликте названия и оборудования. Это эвристические предупреждения: среди них есть
ложные срабатывания, например «Гиперэкстензии без тренажера».
Пять контрольных запросов дают recall@5=1.0; это небольшой регрессионный набор,
а не доказательство качества всех запросов. Исправление исходных карточек — отдельная задача.

Свободные медицинские ограничения и пожелания учитывает модель. Backend не проверяет
медицинскую пригодность программы и не гарантирует тренировочную оптимальность.

## Диагностика и конфигурация

Backend хранит запрос/ответ, статус, причину отказа, вызовы инструментов, аргументы,
результаты и время исполнения. Ключ не попадает в логи/фронт. Пользователю возвращается
понятная ошибка с возможностью повторить или продолжить вручную.

`OPENROUTER_API_KEY`, `OPENROUTER_MODEL`, `OPENROUTER_BASE_URL` задаются на сервере.
`OPENROUTER_MAX_TOKENS` по умолчанию 4096, допустимый предел 256–8192. Если OpenRouter
отклоняет резервирование с 402 и явно сообщает меньший доступный бюджет, выполняется
одна попытка с уменьшенным лимитом. Недостаток средств, 401, 429, тайм-аут и обрезанный
ответ диагностируются отдельно. Неподдерживаемые возможности модели не эмулируются
случайным выбором упражнений.

## Рекомендации после тренировки

В `post_workout_review` LLM только объясняет решения backend policy engine; её actions
не принимаются, инструменты редактирования не включаются. По умолчанию показываются
проверенные предложения с обязательным подтверждением; явный режим сравнения остаётся
доступен для аудита. Модель получает понятные объяснения решений вместо внутренних кодов,
снимков доказательств и переключателей режима. Полные данные сохраняются в backend-журнале.
Контракт, режим сравнения,
журнал и сценарии описаны в [workout-progression.md](workout-progression.md).

## Диалог после разбора статистики (06.11.2026)

Первый запрос — `post_workout_review`, продолжение — `post_workout_chat`. В продолжении
сохраняются статистика и история, доступны read-only tools и ручные pending-правки
по явному запросу пользователя. Информационные вопросы не отменяют ранее подготовленное
предложение. Текст новой ручной правки строится из валидных действий и фактического
плана; сохранение происходит только через apply. Старые клиенты поддерживаются через
переход после первого ответа. Подробности — [workout-progression.md](workout-progression.md).
